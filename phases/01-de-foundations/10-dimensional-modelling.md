## A. Concept deep dive

### 1. The simplest explanation

- A **fact table** records **business events or measurements** — things that happened and can be counted or summed (an order line, a payment, a flight).
- A **dimension table** describes the **context** of those events — who, what, where, when (customer, product, store, date).
- A **star schema** is one fact table in the middle, joined directly to its dimension tables around it.

```
                 dim_date
                    │
 dim_customer ── fact_order_line ── dim_product
                    │
                 dim_store
```

### 2. Why dimensional modelling exists

Business users ask questions like *"revenue by month, by customer segment, by product category"*. A star schema maps that sentence directly onto the model: **measures** come from the fact, **"by …"** comes from dimensions. Queries are simple (one join per dimension), fast (dimensions are small; in Spark they are usually **broadcast** to every executor — Phase 3), and consistent (everyone uses the same dimensions).

### 3. Grain — always first

> **Grain = what one row of the fact table represents.**

Examples: "one row per order line", "one row per order", "one row per account per day".

Declare it **before** choosing columns. Mixing grains is the most common modelling bug:
- If the fact is at **order** grain, you can't store a per-line discount without duplicating or losing information.
- If you put an order-level shipping fee on every **line**, summing it multiplies the fee by the number of lines.

Rule of thumb: choose the **lowest (most detailed) grain** the source supports; aggregates can always be built from it, never the other way round.

### 4. Fact table types

| Type | One row = | Example | Behaviour |
|---|---|---|---|
| **Transaction** | One event | An order line, a payment | Insert-only, most common |
| **Periodic snapshot** | State at regular intervals | Account balance per account per day; stock per product per day | One row per period even if nothing happened |
| **Accumulating snapshot** | One process instance through its milestones | Order: placed → paid → shipped → delivered dates | Rows **updated** as milestones happen |
| **Factless** | An event with no numeric measure | Student attended class; product on promotion | You count rows |

### 5. Measures — additivity

| Kind | Can be summed across… | Example | Trap |
|---|---|---|---|
| **Additive** | All dimensions | quantity, line_amount | — |
| **Semi-additive** | Some dimensions, **not time** | account balance, stock level | Summing daily balances over a month gives nonsense; use end-of-period or average |
| **Non-additive** | None | unit price, ratios, percentages, distinct counts | Store the components (numerator, denominator) and compute the ratio after aggregating |

### 6. Dimensions in depth

| Concept | Meaning | Why |
|---|---|---|
| **Natural (business) key** | Key from the source, e.g. `customer_id = 'C1'` | Identifies the real-world entity |
| **Surrogate key** | Meaningless integer generated by the warehouse, e.g. `customer_sk = 17` | Independent from source key changes/collisions across systems; **required for SCD Type 2**, where one customer has several versions (Phase 9); compact join key |
| **Unknown member** | Row with `sk = -1` ("Unknown") | Fact rows with a missing/late dimension still join and aren't lost |
| **Conformed dimension** | One dimension shared by many facts (same `dim_customer` for orders, payments, support tickets) | Consistent "by customer" across all reports — drill-across |
| **Degenerate dimension** | An identifier kept in the fact with no dimension table (`order_id`) | Group lines into orders without a pointless one-column dimension |
| **Date dimension** | Generated calendar with attributes (month name, quarter, weekend, fiscal period, holidays) | Business calendar logic in one place, not in every query |
| **Junk dimension** | Small flags combined into one dimension | Avoids many tiny dimensions |
| **Slowly changing dimension (SCD)** | How attribute changes are handled: Type 1 overwrite, Type 2 keep history | Phase 9 |

### 7. Star vs snowflake

| | Star | Snowflake |
|---|---|---|
| Dimensions | Denormalised (category name inside `dim_product`) | Normalised (`dim_product → dim_category → dim_department`) |
| Joins | Fewer | More |
| Storage | Slightly more (repeated values — cheap with columnar compression) | Slightly less |
| Query simplicity / speed | Better | Worse |
| Typical choice in a lakehouse | ✅ | Rarely |

### 8. Modelling approaches (vocabulary)

| Approach | Idea | Where it fits |
|---|---|---|
| **Kimball** (dimensional) | Build star schemas per business process, linked by conformed dimensions; bottom-up | Gold layer, BI |
| **Inmon** | Normalised enterprise data warehouse first (3NF), data marts derived from it; top-down | Large enterprises, integration-heavy |
| **Data Vault** | Hubs (keys), links (relationships), satellites (attributes with history); highly auditable, load-friendly | Silver/integration layer with many changing sources |
| **One Big Table (OBT)** | Fully denormalised wide table for one use case | Gold for a specific dashboard/ML feature set; simple but duplicative |

In a medallion lakehouse a common combination is: **Silver = cleaned entities (sometimes Data Vault)**, **Gold = Kimball star schemas and/or OBTs**.

### 9. Misconceptions

1. **"Facts are numbers, dimensions are text."** Facts can contain text identifiers (degenerate dimensions); dimensions can contain numbers (age band, credit limit). The difference is *event vs context*.
2. **"Use the source ID as the key, surrogate keys are old-fashioned."** Without surrogate keys you can't do SCD2 or integrate sources with colliding IDs.
3. **"Normalise the dimensions to save space."** Columnar storage compresses repetition; extra joins cost more than the space saved.
4. **"Grain can be decided later."** Grain determines every column and every aggregation; changing it later means rebuilding.

## B. Practical — build and query a star schema

**Runnable SQL notebook:** [`exercises/phase-01/10_star_schema.sql`](../../exercises/phase-01/10_star_schema.sql)

### Key parts explained

```sql
CREATE TABLE dim_customer (
  customer_sk  BIGINT GENERATED BY DEFAULT AS IDENTITY,
  customer_id  STRING NOT NULL,
  name STRING, city STRING, segment STRING
);
INSERT INTO dim_customer (customer_sk, customer_id, name, city, segment)
VALUES (-1, 'UNKNOWN', 'Unknown', 'Unknown', 'Unknown');
```
- **Identity column** generates surrogate keys automatically. `BY DEFAULT` allows an explicit value, so we can insert the **-1 Unknown member** (`GENERATED ALWAYS` would reject it).
- Identity values are unique and increasing but **not guaranteed consecutive** — never rely on them having no gaps.

```sql
CREATE TABLE dim_date AS
SELECT CAST(date_format(d, 'yyyyMMdd') AS INT) AS date_sk, d AS date, year(d) AS year, ...
FROM (SELECT explode(sequence(DATE'2026-01-01', DATE'2026-12-31', INTERVAL 1 DAY)) AS d);
```
- `sequence` builds an array of dates; `explode` turns it into one row per day. The date key is a readable **smart key** (`20261016`) — a common exception to "surrogate keys are meaningless".

```sql
INSERT INTO fact_order_line
SELECT s.order_id, s.line_no,
       CAST(date_format(s.order_date, 'yyyyMMdd') AS INT) AS date_sk,
       COALESCE(c.customer_sk, -1) AS customer_sk,
       COALESCE(p.product_sk, -1)  AS product_sk,
       s.quantity, s.unit_price, s.discount,
       s.quantity * s.unit_price - s.discount AS line_amount
FROM stg_order_lines s
LEFT JOIN dim_customer c ON s.customer_id = c.customer_id
LEFT JOIN dim_product  p ON s.product_id  = p.product_id;
```
- **Surrogate-key lookup**: translate each natural key into its surrogate key.
- **LEFT JOIN + COALESCE(-1)**: order 1003's customer C9 isn't in the dimension yet → it gets the Unknown member instead of disappearing.
- `line_amount` is precomputed and **additive**; `unit_price` is kept but must never be summed.

## C. Interview questions

### 🟢 Basic

**B1.** What is the difference between a fact table and a dimension table?

<details><summary>Model answer</summary>

A fact table stores business events or measurements at a declared grain — foreign keys to dimensions plus measures such as quantity and amount. A dimension table stores descriptive context (who, what, where, when) used to filter and group facts, such as customer, product and date.
</details>

**B2.** What is the grain of a fact table, and why decide it first?

<details><summary>Model answer</summary>

What one row represents (e.g. one order line). It determines which dimensions and measures are valid and how aggregations behave; mixing grains causes double counting or lost detail, and changing it later means rebuilding the table.
</details>

**B3.** What is a star schema and why is it preferred over a snowflake schema for analytics?

<details><summary>Model answer</summary>

A fact table joined directly to denormalised dimension tables. Fewer joins make queries simpler and faster; dimensions are small enough to broadcast; columnar compression makes the redundancy cheap.
</details>

### 🟡 Medium

**M1.** Why use surrogate keys instead of the source system's customer_id?

<details><summary>Model answer</summary>

They decouple the warehouse from source keys (which can change, be reused, or collide across systems), enable SCD Type 2 where one customer has multiple versions each needing its own key, allow an "Unknown" member (-1), and are compact join keys.
</details>

**M2.** Explain additive, semi-additive and non-additive measures with examples.

<details><summary>Model answer</summary>

Additive: can be summed across all dimensions (quantity, sales amount). Semi-additive: summable across some dimensions but not time (account balance, inventory level — use end-of-period or average over time). Non-additive: can't be summed (unit price, ratios, percentages) — store components and compute after aggregating.
</details>

**M3.** A fact row arrives for customer C9, who isn't in `dim_customer` yet. What are your options?

<details><summary>Model answer</summary>

(1) Map to an Unknown member (-1) and re-key later when the customer arrives; (2) create an "inferred"/placeholder dimension row for C9 immediately and fill its attributes when the real record arrives; (3) hold the fact in a pending table until the dimension arrives. Never silently drop it with an inner join.
</details>

### 🔴 Tricky

**T1.** A periodic-snapshot table stores daily account balances. An analyst reports March balance = SUM(balance) for March. What's wrong and what's correct?

<details><summary>Model answer</summary>

Balance is semi-additive: summing 31 daily balances gives 31× a balance — meaningless. Correct: the balance on the last day of March (closing balance), or the average daily balance, depending on the business question. Summing across accounts on a single day is fine.
</details>

**T2.** The fact table is at order-line grain. Someone adds the order-level `shipping_fee` to each line. What happens in reports, and how should it be modelled?

<details><summary>Model answer</summary>

Summing it multiplies the fee by the number of lines (order 1001 with 2 lines shows 20.00 instead of 10.00). Options: store it in a separate order-grain fact table (`fact_order`), or allocate it across lines (e.g. proportional to line amount) so the sum is correct — a business decision to document.
</details>

**T3.** Why might a lakehouse team build a "one big table" in Gold despite having a star schema?

<details><summary>Model answer</summary>

For a specific consumer — e.g. a dashboard tool or ML model that performs better or is simpler with one wide pre-joined table, or users who don't write joins. It trades storage/duplication and flexibility for simplicity and speed. It should be derived from the star schema/Silver so definitions stay consistent.
</details>

## E. Revision summary

- **Grain first.** Lowest practical grain.
- Fact types: transaction, periodic snapshot, accumulating snapshot, factless.
- Measures: additive, **semi-additive (not over time)**, non-additive (store components).
- Dimensions: natural vs **surrogate** keys, **Unknown member**, conformed, degenerate, date dimension, SCD.
- Star > snowflake for analytics; Kimball in Gold; Data Vault / entities in Silver; OBT for specific consumers.
